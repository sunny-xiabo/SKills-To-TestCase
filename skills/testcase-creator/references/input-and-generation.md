# 输入与用例生成

本文件适用于**全量新建**模式。增量变更见 `change-workflow.md`。

## 阶段 1：需求与设计输入

向用户展示：

```text
【阶段 1 — 需求与设计输入】
请选择需求来源（可多选）：
  A. 直接粘贴文字需求描述
  B. 乐享页面链接
  C. 接口文档链接或本地文件
  D. 本地技术方案或设计稿 PDF（.md / .docx / .pdf）
  E. 图片或设计稿截图（.png / .jpg / .jpeg / .gif / .webp）
  F. 飞书文档链接
  G. Excel 需求列表（.xlsx / .xls）
  H. 需求管理工具链接（Jira / Tapd / 禅道）
  I. 代码（目录/文件路径，和/或 git diff）— 从实现反推测试点

设计稿请导出为 PDF（D）或图片（E），可与其他来源组合提供。
代码（I）须限定范围，禁止无范围全仓扫描。
请输入来源类型并提供对应内容：
```

### 文件读取规则

- PDF：macOS/Linux/WSL 使用 `pdftotext '<路径>' -`；Windows 可使用 pdfplumber。设计稿 PDF 还必须渲染并查看相关页面。
- DOCX：macOS 可使用 `textutil -convert txt -stdout '<路径>'`；其他环境使用 python-docx。
- Markdown：直接读取文件。
- Excel：使用 openpyxl 遍历工作表和单元格，保留工作表名称与来源行。
- 图片：使用可用的图像读取工具识别内容并检查布局。
- 飞书、Jira、Tapd、禅道等链接：使用环境中可用的浏览或获取工具；无法访问时明确说明，不得猜测内容。
- **代码（来源 I）**：见下方「来源 I：代码」。

多来源必须保留来源归属并合并分析。需求和设计同时存在时，交叉检查字段、文案、交互、状态和业务规则。  
**有代码 + 文字需求时**：交叉检查「需求与代码」；不得用代码覆盖未确认的需求描述。  
**仅有代码、无文字需求时**：测试对象与规则以代码分析确认稿为准，并在完备性表中标明「需求正文：未提供」。

### 来源 I：代码（范围强制）

用户必须提供至少一种范围，否则中止并提示补充：

1. **路径**：一个或多个目录/文件（相对业务项目根）  
2. **diff**：`git diff`（工作区或相对 `--base`，如 `origin/main`）

**禁止**在未指定路径且未指定 diff 时扫描整个仓库。

推荐先跑扫描脚本（输出清单+摘录，供分析，**不是用例**）：

```bash
# 指定模块/文件
python3 .testcase-assets/scripts/scan_code_scope.py \
  --path <模块或文件路径> \
  --output <运行目录或临时>/0-代码范围扫描.md

# 或：当前变更
python3 .testcase-assets/scripts/scan_code_scope.py \
  --git-root . --diff \
  --output <运行目录或临时>/0-代码范围扫描.md

# 或：相对主干
python3 .testcase-assets/scripts/scan_code_scope.py \
  --git-root . --diff --base origin/main \
  --output <运行目录或临时>/0-代码范围扫描.md
```

也可在范围很小（如单文件）时由 Agent 直接读取文件，但仍须在完备性表中写明范围。

基于扫描结果（或直接阅读）输出 **代码分析**（须进入确认稿，等人确认）：

```markdown
### 代码分析

- **分析范围**：[路径列表 / diff base]
- **入口与路由/接口**：…
- **关键字段与校验**：…
- **分支与状态**：…
- **权限与角色**：…
- **异常与错误码**：…
- **风险点**：…
- **建议覆盖场景**：正向 / 异常 / 边界 / 并发（说明依据）
```

硬约束：

- 不得把扫描脚本输出直接当作用例表。  
- 不得生成自动化测试代码（pytest/selenium 等）。  
- 代码分析有误时用户可纠正，纠正后再进入阶段 2。  
- 阶段 2 推荐检查点时，`--text` 须包含代码分析中的关键字段、接口与风险点摘要。

### 解析输出

```markdown
## 需求与设计解析结果（请确认）

- **测试对象**：[功能名称/模块]
- **业务规则**：
  1. [规则1]
  2. [规则2]
- **限制条件**：[限制条件]
- **接口/端点**：[如有]
- **涉及角色**：[角色]

### 输入完备性

| 来源 | 状态 | 说明 |
|------|------|------|
| 需求正文 | OK / 降级 / 失败 / 未提供 | … |
| 设计稿 | OK / 降级 / 失败 / 未提供 | 如：无 pdftotext，仅弱解析 |
| 外部链接 | OK / 失败 / 未提供 | 失败则待用户粘贴，禁止编造 |
| 代码（I） | OK / 降级 / 失败 / 未提供 | 须写明路径或 diff 范围；失败不得编造实现 |

### 设计稿分析

- **设计范围**：[文件 / 页面 / 节点]
- **页面与流程**：[入口、流转、关键路径]
- **组件与字段**：[表单、按钮、列表、弹窗]
- **交互与状态**：[默认、加载、空、禁用、错误、成功]
- **视觉与适配**：[层级、间距、颜色、字号、多端差异]
- **校验与反馈**：[输入约束、错误文案、操作反馈]

### 代码分析

（来源含 I 时必填；结构见上文「来源 I」模板）

### 需求与设计差异

| 类型 | 需求描述 | 设计表现 | 影响/待确认项 |
|------|----------|----------|---------------|
| 缺失/冲突/补充 | [需求] | [设计] | [测试影响] |

### 需求与代码差异

| 类型 | 需求/设计描述 | 代码表现 | 影响/待确认项 |
|------|---------------|----------|---------------|
| 缺失/冲突/补充 | … | … | … |

（无文字需求或无代码时，对应差异表可省略。）

[OK] 若解析正确，请回复“确认”继续阶段 2。
[FAIL] 若需修正，请指出错误内容。
```

未提供设计稿时省略设计稿分析和「需求与设计差异」表。  
未提供代码时省略代码分析与「需求与代码差异」表。  
用户确认后清理模块名中的 `/ \ : * ? " < > |`，创建运行目录；若已生成 `0-代码范围扫描.md`，确认后复制或移入该运行目录保留溯源。

## 阶段 2：输入结构化

分 2a 检查点推荐与 2b 历史复用两步；均须用户确认，不得静默跳过确认门。

### 2a 检查点选择（含推荐）

读取 `.testcase-assets/checkpoints-index.md`。优先用脚本生成可解释推荐：

```bash
python3 .testcase-assets/scripts/recommend_checkpoints.py \
  --checkpoints .testcase-assets/checkpoints-index.md \
  --text "<测试对象+业务规则+设计要点>" \
  --rules .testcase-assets/recommend-rules.yaml \
  --output <运行目录>/2a-检查点推荐.md
```

规则文件可从 `templates/recommend-rules.yaml` 复制到 `.testcase-assets/` 后按项目修改。  
推荐须展示**命中原因**；排除 `[已废弃]`；上限见规则 `max_recommend`。

```text
【阶段 2a — 检查点选择】
已根据规则预推荐（可改）：
  [*] LIST-02 ...  ← 设计信号「分页」
  [ ] FILE-01 ...（未推荐，可手选）

请输入：编号列表 / 采用推荐 / 全选 / 跳过
```

默认快捷回复为「采用推荐」，不是静默自动确认。

### 2b 历史用例复用（可选，两级）

**一级选目录，二级选用例**，禁止一次扫描灌入全部 history 全文。

```bash
python3 .testcase-assets/scripts/recommend_history.py \
  --history-root .testcase-assets/history --module "<测试对象>" \
  --rules .testcase-assets/recommend-rules.yaml --list-dirs --limit 10

python3 .testcase-assets/scripts/recommend_history.py \
  --history-root .testcase-assets/history --dir <选定目录名> --list-cases
```

```text
【阶段 2b — 历史用例复用】（可跳过）
一级目录候选 → 用户选定后 → 二级用例列表（ID/测试点/类型/优先级）
请输入要复用的编号（可多选），或回复“跳过”
```

**未经用户勾选，不得复制任何历史用例。**  
增量变更模式跳过 2b。

## 阶段 3：用例生成

读取 `.testcase-assets/templates/testcase-table-config.json` 的 `columns` 和 `optional_columns`。文件不存在时使用：用例ID、所属模块、测试点、前置条件、操作步骤、预期结果、关联检查点、场景类型、优先级。

生成要求：

- 覆盖需求业务规则及设计中明确呈现的流程、字段、状态、适配和反馈。
- 若有代码分析：覆盖其中已确认的入口、校验、分支、权限与异常；未确认的需求/代码差异不得擅自选边。
- 未确认的需求/设计差异不得擅自选边。
- 操作步骤使用从 1 开始、连续且不重复的编号。
- 预期结果必须可验证；避免“正常”“正确”“符合预期”“适当”“相关提示”等没有明确判定标准的措辞。
- UI 控件统一使用中文术语“按钮”，不要混用 `button`。
- 同一条用例统一使用中文双引号 `“”`，不要混用英文双引号或其他引号样式。
- 若步骤和预期均为多项，使用相同编号建立对应关系。
- 备注列存在时，所有生成用例必须留空。
- 优先级默认：P0=异常，P1=正向主流程/边界，P2=并发，P3=体验类。

### 历史复用合并规则

若阶段 2b 有勾选：

1. 将被选历史用例纳入初稿（可按新需求微调步骤/预期）。
2. **本轮统一重新编号**（如从 TC-001 起），在 `0-用例准备.md` 回填映射：`本轮 TC-00x ← 历史 TC-yyy`。
3. 映射与来源说明不得写入备注列。
4. 仅为尚未覆盖的规则、检查点或场景类型生成新行。
5. 不得把未勾选的历史用例带入表中。

```markdown
## 测试用例表（初稿）

| 用例ID | 所属模块 | 测试点 | 前置条件 | 操作步骤 | 预期结果 | 关联检查点 | 场景类型 | 优先级 |
|--------|----------|--------|----------|----------|----------|------------|----------|--------|
| TC-001 | 用户中心 | 找回密码 | 用户已注册 | 1. 输入手机号\n2. 获取验证码\n3. 设置新密码 | 1. 验证码发送成功\n2. 新密码保存成功\n3. 跳转登录页 | UC-01 | 正向 | P1 |

> 共生成 X 条用例，覆盖正向 X / 异常 X / 边界 X / 并发 X 条
> 其中复用历史 X 条，新编写 X 条

[OK] 请回复“进入评审”，或指出需要修改的用例。
```

写入 `<运行目录>/1-评审记要.md`。不得把审计信息写入备注列。
